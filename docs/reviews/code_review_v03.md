## Persona 1: Python Principal Developer

### v03-P2-01 - Global-identity admission is still partial in bounding and difficulty telemetry

**Evidence**

- `forge/src/boxscore_forge/solver.py:347` correctly tries propagation without the global identity before trying the whole system.
- `forge/src/boxscore_forge/solver.py:345` nevertheless computes `live` and `solvable` over the whole system before it knows which phase supplied the chosen move.
- Those whole-system counts are stored on a deduction selected from the non-global phase at `solver.py:359-360`.
- `forge/src/boxscore_forge/solver.py:367` calls `_bounding_moves()` without a phase-specific equation set.
- `forge/src/boxscore_forge/solver.py:415` calls `narrow(shape, values)`, which builds domains from the full equation system, including the global identity.
- The comment at `solver.py:364` says bounding uses the whole system, while `_bounding_moves()` at `solver.py:412` says the global identity stays out. The implementation follows the former, not the latter.

**Why this matters**

The propagation-order portion of v02-P2-01 was fixed, but the phase boundary remains incomplete in two places.

First, a local deduction's search cost includes a global equation that the player is intentionally not expected to consider yet. This changes the difficulty telemetry even when the chosen cell is correct.

Second, bounding can use the global identity before non-global bounding has reached its own fixed point. A cell fixed through that global contribution is recorded as a generic bounding deduction with `from_identity=None`, so the global family can influence the solve without appearing in `families_used`. Family variety and stall-restart research can therefore under-report use of the global identity.

**Recommendation**

Make the active equation set explicit for propagation, scan-size telemetry, and narrowing. Exhaust non-global propagation and non-global bounding before admitting the global equation, or record the families that contributed to a bound if whole-board bounding is the intended human model. Add tests for:

- a local move whose search cost must exclude a simultaneously solvable global equation;
- a board where non-global and global bounding can both make progress;
- a solution whose global-assisted bound must not be reported as having no global-family involvement.

**Also affects:** Personas 2, 5, and 7.

## Persona 2: QA and Reliability Engineer

### v03-P2-02 - A staged reference batch can overwrite a duplicate puzzle and can commit as a mixed generation

**Evidence**

- `forge/scripts/write_reference_puzzles.py:159` initializes `wanted` with the first substitution board and the first live-footnote board without checking whether they are the same game.
- `write_reference_puzzles.py:160` creates `seen` only after both entries have already been appended, so it does not remove that duplicate.
- Both entries derive the same `puzzle_id` at `write_reference_puzzles.py:80` and write to the same staged path at `write_reference_puzzles.py:186-187`.
- `written` counts successful write attempts rather than unique staged filenames, so the six-attempt check at `write_reference_puzzles.py:210` can pass with only five files in staging.
- `_publish()` replaces files one at a time at `write_reference_puzzles.py:132-138`. A process failure halfway through leaves a mixture of old and new generations; the directory swap is not atomic as a batch.

**Why this matters**

The current six reference files happen to have unique IDs, but uniqueness is an accidental property of the present sample ordering. A future sample in which one direction carries both required traits can silently overwrite one target with another and still report six successful writes. Separately, staging protects the old set while generation is running, but not while the staged set is being committed.

This is narrower than v02-P2-04: truncated individual files and the initial empty-directory window were fixed. The remaining problem is uniqueness and atomicity of the set as a whole.

**Recommendation**

Select required traits through a `claim()` operation that refuses an already-used game before appending. Assert unique game IDs, unique puzzle IDs, and exactly six staged filenames before commit. For a production inventory, publish immutable versioned directories and atomically replace one manifest/current-version pointer; per-file atomic renames cannot provide batch atomicity.

**Also affects:** Personas 1 and 5.

### v03-P2-03 - The package envelope still accepts malformed identifiers, signatures, and schema values

**Evidence**

- `forge/src/boxscore_package/format.py:339` still declares `Package.from_json(raw: dict[str, Any])` and immediately calls `raw.get`; a direct call with any other parsed JSON root raises `AttributeError` rather than `PackageError`.
- `format.py:346` copies `puzzle_id` without checking that it is a string or the contract's 16 hexadecimal characters.
- `format.py:354` copies `signature` without checking that it is a string or a 64-character hexadecimal HMAC.
- `format.py:340-343` accepts `true` as schema 1 because Python treats `bool` as an `int` and `True == 1`.
- `read()` protects its own root-object path, but `Package.from_json()` is a public boundary and remains unsafe when called directly.

**Why this matters**

The v01 boundary fix validates board internals well, but the package envelope still does not match `docs/package-format-v1.md`. A malformed signature can reach `hmac.compare_digest()` with the wrong type and crash instead of being rejected. A malformed ID can reach filenames, logs, caches, or future URL construction. This is currently an offline reliability defect, not an exploitable endpoint, because `serve` has no implementation yet.

**Recommendation**

Accept `object`, reject non-dict roots, and validate every envelope field at construction: exact non-boolean schema integer, opaque ID matching `[0-9a-f]{16}`, and optional signature matching `[0-9a-f]{64}`. Add direct `Package.from_json()` tests, not only `read()` tests, for list/null roots, boolean schema, non-string IDs, path-like IDs, and non-string signatures.

**Also affects:** Personas 1, 3, 4, and 5.

## Persona 4: Security Engineer

### v03-P2-04 - HMAC gives the serving tier the authority to forge inventory

**Evidence**

- `forge/src/boxscore_package/signing.py:18-19` deliberately chooses HMAC-SHA256 with the same secret on the laptop and VPS.
- The architecture in `CLAUDE.md` says only the forge laptop may produce puzzle inventory and the service may only serve what it receives.
- With a symmetric MAC, every verifier is also capable of producing a valid authenticator. Possession of the VPS verification secret is therefore possession of the forge's signing authority.

**Attack scenario**

An attacker obtains read access to the VPS environment, a deployment backup, a diagnostic dump, or another location containing `BOXSCORE_SIGNING_SECRET`, and also obtains any path that can replace or inject a puzzle JSON file.

**Exploitation method**

The attacker constructs a forged package containing altered answers, reveal content, metadata, or puzzle values, computes the canonical JSON exactly as `canonical_bytes()` does, and signs it with the stolen HMAC key. The service cannot distinguish that package from one produced on the forge laptop.

**Business impact**

The attacker can corrupt the daily game, publish false historical content, spoil answers, or place malicious text into fields later rendered by the frontend. It also defeats the stated environment boundary: compromise or leakage of a read-only verification secret becomes authority to create inventory.

**Recommended fix**

Use an asymmetric signature such as Ed25519. Keep the private signing key only on the forge machine and deploy only the public verification key to `serve`. Include a key ID/version in the signed envelope to support rotation. Rotate the current shared secret before production if it has ever left the local reference-fixture workflow.

**Reasoning**

HMAC is cryptographically strong, and no weakness in SHA-256 or `compare_digest()` was found. The problem is authority placement: a MAC proves that either party holding the shared key produced the message, while the architecture needs proof that only the forge did.

**Also affects:** Persona 5.

No current findings apply to authentication, sessions, CSRF, authorization, rate limiting, SSRF, uploads, redirects, or tenant isolation because none of those surfaces exists yet. A fresh OWASP review is required when `serve` contains an application or API.

## Persona 5: Backend Architect

### v03-P1-01 - Publication evidence is neither bound to a game nor complete enough to establish correspondence

**Evidence**

- `forge/src/boxscore_verify/certify.py:40-51` defines `Evidence` with source type, a deduced flag, and only the offense's official hits and runs. It carries no game ID, team/direction, expected puzzle ID, defensive totals, or error totals.
- `certify.py:97-114` compares only `line_score.offense_hits` and `line_score.offense_runs` with that evidence.
- `discovery/difficulty-metrics/measure.py:293-295` correctly filters on the database's separate `p.is_deduced` column.
- `Loaded` retains `source_type` at `measure.py:104` but does not retain the actual `is_deduced` value.
- `forge/scripts/write_reference_puzzles.py:118` reconstructs the flag with `loaded.source_type.startswith("ED")`, even though source type and `is_deduced` are separate provenance facts in the schema.
- Nothing in `certify_for_publication()` proves that an `Evidence` object belongs to the package being certified. Evidence from a different game with the same offensive R/H totals can satisfy the gate.

**Why this matters**

The new certification boundary is intended to catch a loader or adapter that produces a self-consistent but historically wrong package. It currently trusts an unbound assertion from that same producer:

- a package/evidence mix-up can pass when two games share the same offensive run and hit totals;
- a future loader regression that admits a deduced `EVA`, `EVN`, or `EVF` record will pass `is_deduced=False`, because the writer derives the flag from the source name rather than the provenance row;
- altered defensive runs, defensive hits, and either side's error total are outside the correspondence check even though the complete line score is player-visible and signed.

This is a new contract gap introduced by the v02-P1-06 repair, not a repetition of the former absence of a publication gate.

**Recommendation**

Carry an immutable source-evidence record containing at least game ID, batting team/direction, the actual database `is_deduced` value, source type, expected opaque puzzle ID, and all official player-visible line-score fields. Recompute the expected puzzle ID from evidence and compare it with the package. Compare the complete R/H/E block and inning arrays against independent source values where available. Add tests that deliberately swap evidence between two games, pass a deduced record with an accepted source type, and alter each currently unchecked defensive/error field independently.

**Also affects:** Personas 2, 4, and 6.

## Persona 7: Kakuro and Logic-Puzzle Specialist

### v03-P1-02 - Active research still uses three different definitions of the erasable board

**Evidence**

- The canonical engine includes per-batter footnote cells at `forge/src/boxscore_forge/erasure.py:53-74`.
- `discovery/difficulty-metrics/measure.py:446-453` still implements a local `erasable_cells()` that includes only batting and pitching grids and says footnotes are given.
- `discovery/stall-targeted/measure.py:112-120` starts with the canonical `erasable()` list and then appends every footnote cell again.
- `discovery/stall-targeted/measure.py:128` passes that duplicated list into `row_first`, whose per-row shuffle now gives footnote cells two positions and changes the seeded order of the other cells.
- The production `erase(target_stalls=...)` path uses the canonical unique list, so the discovery result is not measuring the same generator that writes reference packages.

**Why this matters**

The v02 adapter fix correctly preserves footnote blanks in packages, but the research instruments were not fully migrated. One experiment never erases footnotes; another weights them twice and performs repeated no-op solves; production includes them once. Stall ceilings, blanks required for a target, trivial share, family use, and seeded trajectories are therefore not directly comparable.

This residual was mentioned in v02-P1-01 but is still present despite the backlog marking that repair closed. The regenerated `discovery/stall-targeted/results.txt` must not be treated as canonical evidence until the candidate set is corrected.

**Recommendation**

Delete local erasable-cell implementations and consume `boxscore_forge.erasure.erasable()` everywhere a current generator is being measured. Assert that the candidate list is unique and equals the canonical set. Historical experiments that intentionally model the old board should freeze and name that model explicitly rather than use current terminology. Regenerate every affected difficulty, compressibility, stall, and footnote result after the correction.

**Also affects:** Personas 1, 2, 5, and 8.

### v03-P2-05 - The RBI/HR comparison changes erasure trajectories and applies zero density asymmetrically

**Evidence**

- `discovery/rbi-and-hr/measure.py:33-36` claims that every configuration solves the same boards and that the columns are the only difference.
- Each variant rebuilds a different candidate list and then calls `row_first` with the same seed at `measure.py:492-499`.
- Adding columns changes every row bucket's length. Shuffling with the same seed does not preserve the order of the common cells, so each variant follows a different erasure trajectory.
- The entire comparison uses one seed (`SEED` at `measure.py:70` and “one seed” at `measure.py:625`).
- `zero_density()` at `measure.py:409-421` counts batting and pitching rows only. An HR batting column contributes its very high zero rate, while the equivalent per-batter HR footnote does not, despite the report describing zero density over each configuration's own cells.

**Why this matters**

The games are paired, but the blank-removal paths are not. A reported gain or loss can come from a different shuffle of the original six columns rather than from RBI/HR constraints. With one seed there is no averaging that can separate that ordering noise. The zero-density comparison also structurally favors the footnote placement unless the gate is explicitly defined as grid-only; the current report presents it as a full-configuration comparison.

**Recommendation**

Create one stable priority permutation for the base cells and preserve it across variants, with separately controlled insertion positions for new cells. Run multiple seeds and report paired per-game deltas with spread or confidence intervals, not medians alone. Decide and state whether zero density is a grid-visual metric or an all-erasable-cell metric; then apply that same denominator to every placement. Do not use the current partial run to settle the v1 column set.

**Also affects:** Personas 2, 5, 6, and 8.
